# 문서 사이트 작업 재개

WBS 파일: `WBS.md` (저장소 루트)

**작업 브랜치는 `dev` 뿐이다.**
`main` 은 사용자가 직접 검토하고 올린다. **`main` 으로 checkout·병합·push 하지 않는다.**
WBS 항목에 "main 반영" 이 적혀 있어도 마찬가지다. 그건 사용자가 할 일이니
준비가 끝났다고 알리기만 한다.

## 1. 현재 위치 파악

`WBS.md` 를 읽는다. **"▶ 지금 할 것"** 항목이 다음 작업이다.

이 저장소를 처음 여는 세션이면 `HANDOFF.md` 도 같이 읽는다. 환경 준비와 지금 상태가 정리돼 있다.

- 인자로 ID가 주어졌으면(`/cwc-next S6-1`) 그 항목을 대신 진행한다
- 인자가 `status` 면 현황만 요약하고 끝낸다
- ⏸️ 항목은 앞 항목이 ✅ 가 되기 전에 착수하지 않는다

## 2. 작업

- **해당 항목만** 한다. 눈에 띈 다른 문제는 고치지 말고 WBS에 새 항목으로 추가한다
- 시작할 때 상태를 🔄 로 바꾼다
- 한 번에 파일 하나씩 고친다. 고치기 전에 무엇을 왜 바꾸는지 한 줄로 먼저 말한다
- WBS에 적힌 근거(줄 번호 등)를 믿지 말고 **파일을 다시 열어 확인**한다. 그 사이 바뀌었을 수 있다

## 3. 검증 팀 회의 (건너뛰지 않는다)

WBS의 "검증" 칸에 적힌 팀원을 부른다. 여러 명이면 **한 메시지에서 동시에** 부른다.

| 팀원 | 언제 부르나 |
|---|---|
| `doc-guard` | 문서 글을 고쳤을 때 — 말투·중복·강조·가독성 규칙 |
| `newbie-sim` | 회차 문서를 고쳤을 때 — 참가자가 막히는 곳 |
| `fact-check` | 외부 서비스(Vercel·Supabase·GitHub) 안내를 고쳤을 때 |
| `build-check` | 빌드·링크·워크플로·frontmatter 를 건드렸을 때 |

**회의 진행**

1. 팀원들의 보고를 모은다
2. `[심각]` `[막힘]` `[틀림]` `[실패]` 는 **반드시 고친다**
3. 고친 뒤 **같은 팀원을 다시 불러 재확인**한다. 한 번 고치고 통과라고 하지 않는다
4. `[보통]` `[갸웃]` 은 판단해서 고치거나 WBS에 새 항목으로 남긴다
5. `[사소]` 는 무시해도 된다

팀원이 없는 문제를 지어낸 것 같으면 직접 파일을 열어 확인한다. 보고를 그대로 믿지 않는다.

## 4. 세 번 막히면 넘어간다

같은 항목에서 **세 번 시도해도 통과하지 못하면** 멈춘다.

1. 왜 막혔는지 원인을 한두 줄로 정리한다
2. **다음 작업과 연관이 있는지 판단한다**
   - 연관 있음 → 넘어가지 않는다. 사용자에게 무엇이 막혔는지 알리고 판단을 받는다
   - 연관 없음 → 상태를 ⛔ 로 바꾸고 "막힌 기록" 표에 날짜·ID·원인·다시 볼 시점을 적는다
3. 그다음 항목으로 넘어간다

## 5. 기록과 커밋 (통과한 뒤에만)

검증을 통과했으면 **그 자리에서** 아래를 다 한다. 나중으로 미루지 않는다.

1. WBS에서 해당 항목을 ✅ 로 바꾼다
2. **"▶ 지금 할 것"** 을 다음 항목으로 갱신한다
3. "완료 기록" 표에 날짜·ID·내용을 추가한다
4. 고친 파일과 `WBS.md` 를 **함께** 커밋한다 (`dev` 브랜치)
   - 커밋 메시지: `docs: <내용>` 또는 `chore: <내용>` + 본문에 `WBS: <ID>`
5. `dev` push 는 사용자가 요청할 때만 한다. **`main` push 는 어떤 경우에도 하지 않는다**

🔄 를 남긴 채 턴을 끝내지 않는다. 끝내면 훅이 막는다.

## 6. 다음 작업 안내

- 무엇을 고쳤고 팀이 뭘 잡아냈는지 (한두 문장)
- 다음 항목이 무엇인지
- 다음 항목이 직전 항목과 주제가 다르면 이렇게 안내한다

  > 다음은 `<ID> — <제목>` 입니다. 직전 작업과 무관하니 `/clear` 후 `/cwc-next` 로 이어가시면 됩니다.
