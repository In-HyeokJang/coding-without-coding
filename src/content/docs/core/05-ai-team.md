>
> 이 문서는 **선택 사항**입니다. 이 방식 없이도 6회차 커리큘럼은 끝까지 갑니다.

---

## 이게 뭔가요

혼자서 기획, 디자인, 코딩 결정을 모두 하기 부담스러울 때가 있습니다.

그럴 때는 AI에게 역할을 나누어, 스스로 대화하며 일하는 **'AI 팀'** 을 만들어줄 수 있어요.

한 사람에게 "알아서 잘 만들어줘" 하면 무난한 답이 나옵니다.

그런데 "기획자, 디자이너, 개발자 셋이서 검토하고 합의해서 가져와" 하면, AI가 스스로 여러 각도에서 따져본 뒤 결과를 내놓습니다.

> **진짜 다른 사람이 여럿 붙는 건 아닙니다.**
> AI 하나가 여러 관점을 번갈아 쓰는 거예요.
> 그래도 결과물의 완성도는 눈에 띄게 달라집니다.

---

## 회차마다 몇 명이 좋은가

**사람을 많이 붙일수록 좋은 게 아닙니다.** 그 회차에 실제로 필요한 관점만 부르는 게 나아요.

| 회차 | 몇 명 | 누구 | 왜 |
|---|---|---|---|
| **3회차 · 뼈대** | 2명 | 기획자 + 개발자 | 디자인은 5회차 것이라 디자이너를 부르면 오늘 할 일이 늘어납니다 |
| **4회차 · 기능** | 팀 없이 | — | 에러 하나 뚫는 데는 팀이 오히려 방해가 됩니다 |
| **5회차 · 다듬기** | 3명 | 기획자 + **디자이너** + 개발자 | 여기서 디자이너를 부릅니다 |

3회차용 2명 프롬프트는 회차 문서 안에 있어요. 아래는 **5회차부터** 쓰시면 됩니다.

---

## 1단계 · 먼저 3명으로

처음부터 크게 갈 필요 없습니다.

이 정도면 충분히 효과가 보여요.

```
너는 이제 3명의 전문가로 구성된 AI 팀이야.

1. 수석 기획자 (사용자 경험과 페이지 구조 검토)
2. UI/UX 디자이너 (색상, 레이아웃, 세련된 모던 디자인)
3. Next.js 개발자 (안정적이고 간결한 코드 작성)

내가 [브런치 카페 리뷰 사이트를 만들고 싶어] 라고 말하면,
기획자가 구조를 정하고, 디자이너가 스타일을 제안하고, 개발자가 최선의 코드를 구현해줘.
셋이 서로 검수하고 합의한 뒤 최종 결과물만 나한테 보여줘.
```

이렇게 지시하면 AI가 단조로운 답 대신, 여러 각도로 검토된 결과물을 만들어줍니다.

> 우리는 **Next.js + TypeScript** 로 만듭니다. 위에 적힌 그대로 쓰시면 돼요.
> `Next.js 개발자` 대신 `Next.js + TypeScript 개발자` 라고 하시면 더 정확합니다.

---

## 2단계 · 익숙해지면 6명으로

3명으로 몇 번 해보고 "좀 더 꼼꼼했으면 좋겠다" 싶을 때 늘립니다.

| 역할 | 무슨 일을 하나 |
|---|---|
| **PM** | 뭘 먼저 만들지 순서를 정하고, 범위가 커지면 잘라냅니다 |
| **기획자** | 사용자가 어떤 순서로 화면을 보게 될지 구조를 잡습니다 |
| **UI/UX 디자이너** | 색상, 간격, 글자 크기를 정하고 톤을 통일합니다 |
| **개발자** | 안정적이고 간결한 코드를 씁니다 |
| **퍼블리셔** | 폰에서 깨지지 않는지, 글자가 읽히는지 봅니다 |
| **QA** | 안 눌리는 버튼, 깨진 링크, 빠진 화면을 찾아냅니다 |

아래를 그대로 복사해서 쓰시면 됩니다.

```
너는 이제 6명으로 구성된 제품 팀이야. 각자 역할은 이래.

1. PM — 이번에 뭘 먼저 만들지 순서를 정하고, 범위가 커지면 잘라낸다
2. 기획자 — 사용자가 어떤 순서로 화면을 보게 될지 구조를 잡는다
3. UI/UX 디자이너 — 색상, 간격, 글자 크기를 정하고 톤을 통일한다
4. 개발자 — 안정적이고 간결한 코드를 쓴다
5. 퍼블리셔 — 폰에서 깨지지 않는지, 글자가 읽히는지 본다
6. QA — 다 만든 뒤에 안 눌리는 버튼, 깨진 링크, 빠진 화면을 찾아낸다

내가 만들고 싶은 걸 말하면 여섯이 각자 의견을 내고,
서로 검토해서 합의한 다음 결과를 보여줘.
```

역할 이름은 그대로 쓰지 않으셔도 됩니다.

**"이 관점으로도 한 번 봐줘"** 를 목록으로 적어준 것에 가까워요.

---

## 3단계 · 내 프로젝트에 맞게 팀을 다시 짜기

위 6명은 예시일 뿐입니다.

만들려는 게 무엇이냐에 따라 필요한 역할이 달라져요.

그래서 **팀 구성 자체를 AI에게 맡기는 방법**이 있습니다.

```
내가 만들려는 건 [여기에 내 프로젝트를 한두 줄로 적기] 야.

이 프로젝트를 끝까지 만들려면 어떤 역할들이 필요할지 네가 정해줘.
- 역할은 최대 6개까지만
- 각 역할이 무슨 일을 하는지 한 줄씩
- 이 프로젝트에 필요 없는 역할은 넣지 마

정하고 나면 그 팀으로 일해줘.
```

이렇게 하면 팀 구성이 프로젝트마다 달라집니다.

사진 위주 사이트에는 디자이너 비중이 커지고, 글이 많은 사이트에는 편집자 역할이 붙는 식이에요.

---

## 4단계 · 일하는 방식을 정해주기

**이 문서에서 제일 중요한 부분입니다.**

팀만 만들어두면 AI가 회의하다가 혼자 코드까지 다 짜버립니다.

그래서 **"어디까지 하고 나한테 물어봐야 하는지"** 를 같이 정해줘야 해요.

```
앞으로 이 팀은 이 순서로 일해줘.

1. 내가 요청하면, 팀끼리 먼저 의논한다
2. 의논한 결과를 '방향 A / 방향 B' 두 가지로 정리해서 나한테 보여준다
3. 내가 하나를 고르기 전까지는 코드를 건드리지 않는다
4. 내가 고르면 그때 개발자가 만든다
5. 만든 다음 QA가 확인하고, 문제가 있으면 나한테 알려준다

회의 내용을 길게 다 보여주지는 말고, 결론과 이유만 짧게 말해줘.
```

이 다섯 줄이 이 방식의 핵심입니다.

**AI가 스스로 판단해서 달려가지 않고, 갈림길마다 나한테 물어보게 되거든요.**

## 역할을 더 붙이고 싶다면

말씀드린 6명 말고도 붙일 수 있는 역할이 있습니다.

다만 **지금 만드는 사이트에 그 일이 실제로 있을 때만** 넣으세요.

| 역할 | 무슨 일을 하나 | 언제 필요한가 |
|---|---|---|
| **API 개발자** | 바깥 서비스에서 데이터를 받아오는 부분을 담당 | 지도, 결제, 로그인처럼 **다른 서비스와 연결**할 때 |
| **DBA (데이터 담당)** | 데이터를 어떤 모양으로 저장할지 정함 | 사용자가 **글을 쓰거나 저장**하는 기능이 있을 때 |
| **초기 세팅 담당** | 폴더 구조, 공통 규칙, 재사용 부품을 먼저 잡음 | 페이지가 **10개 이상**으로 커질 것 같을 때 |
| **에디터 / 카피라이터** | 문구와 말투를 다듬음 | 글이 주인공인 사이트일 때 |

> **6회차 커리큘럼에서 만드는 사이트에는 위 역할이 대부분 필요 없습니다.**
>
> 저장할 데이터도, 연결할 바깥 서비스도 없는 경우가 많거든요.
>
> 없는 역할을 넣으면 AI가 굳이 일을 만들어냅니다. 그래서 오히려 복잡해져요.

---

:::caution[토큰이 평소보다 많이 듭니다]
AI 팀 방식은 한 번 물어볼 때마다 **여러 관점을 다 거쳐서** 답을 만듭니다.

그만큼 대화가 길어지고, 토큰(사용량)도 평소보다 빨리 줄어요.

**아껴 쓰는 요령**

- 회의는 **방향을 정할 때만** 씁니다. 버튼 색 바꾸기 같은 작은 일에는 쓰지 않아요.
- "회의 내용을 다 보여주지 말고 **결론만**" 이라고 미리 말해둡니다.
- 역할은 **최대 6개까지**. 많을수록 답이 길어집니다.
- 방향이 정해지고 나면 `이제 팀 회의는 그만하고 평소처럼 해줘` 라고 하고 돌아옵니다.
:::

## 언제 쓰고, 언제 쓰지 말까

| 이럴 때 | 어떻게 |
|---|---|
| 뭘 만들지는 정했는데 **어떻게 생겨야 할지** 모르겠을 때 | 팀 방식이 잘 맞습니다 |
| 만든 걸 보니 **뭔가 밋밋한데** 어디가 문제인지 모를 때 | 팀 방식으로 다시 보게 하면 좋습니다 |
| 에러 하나 고치기 | 팀 필요 없습니다. 평소대로 물어보세요 |
| 글자 하나 바꾸기 | 팀 필요 없습니다 |

정리하면, **결정이 필요한 순간에만** 팀을 부르시면 됩니다.

나머지는 평소대로 하시는 게 낫습니다.
