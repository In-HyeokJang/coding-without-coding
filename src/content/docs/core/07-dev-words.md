## 이 문서는 뭔가요

회차를 진행하다 보면 AI가 이런 말을 씁니다.

> "커밋했습니다" · "빌드가 실패했어요" · "린트 에러가 있습니다"

**무슨 뜻인지 몰라도 진행은 됩니다.** 다만 알아두면 두 가지가 편해져요.

- AI가 지금 뭘 하고 있는지 보입니다
- 에러가 났을 때 <mark>어느 단계에서 막힌 건지</mark> 짐작이 갑니다

여섯 개뿐이고, 다 일상적인 비유로 설명됩니다.

---

## 한눈에

| 말 | 뭘 하는 일 | 우리가 만나는 곳 |
|---|---|---|
| **커밋** | 지금까지 작업한 걸 저장 | 3회차부터 |
| **푸시** | 저장한 걸 인터넷 창고로 보냄 | 3회차부터 |
| **빌드** | 코드가 진짜 돌아가는지 조립해봄 | 5회차 |
| **배포** | 세상에 공개 | 6회차 |
| **린트** | 코드 맞춤법 검사 | 빌드할 때 같이 걸림 |
| **리팩터링** | 겉은 그대로, 속만 정리 | 선택 사항 |

## 1. 커밋 — 게임 세이브

**지금까지 작업한 걸 하나로 묶어서 저장하는 일**입니다.

게임하다가 중요한 순간에 저장하고, 그 저장 파일에 이름을 붙이는 것과 같아요. 나중에 뭘 바꿨는지 확인하거나, 문제가 생겼을 때 그 지점으로 돌아갈 수 있습니다.

**커밋은 아직 내 노트북 안에만 있습니다.** 인터넷에는 안 올라가요.

**프롬프트**

```
이번에 실제로 바꾼 파일만 골라줘.

아직 커밋하지 말고, 커밋에 들어갈 파일 목록과 커밋 이름을 먼저 보여줘.
다른 작업 파일이 섞이지 않았는지도 확인해줘.

내가 좋다고 하면 그때 커밋해줘.
```

---

## 2. 푸시 — 인터넷 창고로 보내기

**내 노트북에 저장해둔 커밋을 GitHub 같은 온라인 보관함으로 보내는 일**입니다.

커밋이 "내 방 책상에 정리해둔 것"이라면, 푸시는 "그걸 창고에 갖다 두는 것"이에요.

푸시를 해야 6회차에 Vercel이 내 코드를 가져갈 수 있습니다.

**프롬프트**

```
지금 작업한 걸 어느 저장소와 브랜치에 올릴지 먼저 보여줘.
어떤 커밋이 올라가는지도 알려줘.

아직 푸시하지 말고 기다려줘.
내가 좋다고 하면 그때 올려줘.
```

:::caution[푸시하기 전에 `.env` 는 꼭 확인하세요]
`.env` 파일에는 Supabase 열쇠가 들어 있습니다. 한번 GitHub에 올라가면 남이 내 데이터 창고를 열 수 있어요.

```
방금 올린 것 중에 .env 파일이 들어갔는지 확인해줘.
```
:::

---

## 3. 빌드 — 레고 조립해보기

**써놓은 코드가 실제로 돌아가는 형태인지 조립해보는 일**입니다.

레고 설명서를 보고 조각을 하나로 맞춰보는 것과 비슷해요. 빠진 조각이 있거나 서로 안 맞으면 조립이 멈추듯, 빌드도 실패합니다.

**5회차에 이걸 미리 돌려봅니다.** 6회차에 Vercel이 하는 검사와 **같은 검사**라, 여기서 통과하면 배포도 통과해요.

**프롬프트**

```
npm run build 를 실행해서 성공했는지 실패했는지 알려줘.

실패했다면 가장 큰 원인부터, 코딩을 모르는 사람도
이해할 수 있게 설명해줘.

문제를 숨기려고 설정을 마음대로 바꾸지는 마.
```

:::note[마지막 줄이 중요합니다]
빌드 에러는 **설정을 꺼버리면 그냥 통과됩니다.** AI가 그렇게 넘어가버릴 때가 있어요.

그러면 지금은 배포가 되지만, 진짜 문제는 그대로 남아서 나중에 사이트에서 터집니다.

그래서 "숨기지 마" 를 꼭 붙입니다.
:::

---

## 4. 배포 — 세상에 내놓기

**다 만든 결과물을 사람들이 실제로 볼 수 있게 올리는 일**입니다.

지금까지 `localhost:3000` 은 내 노트북에서만 열렸죠. 배포하면 누구나 열 수 있는 주소가 생깁니다.

:::caution["배포 완료" 메시지만 보고 끝내지 마세요]
배포가 끝났다는 말과, 사이트가 제대로 뜨는 건 **다른 이야기**입니다.

실제 주소를 열어서 **화면이 나오는지, 버튼이 눌리는지** 직접 확인하세요. 6회차에 다 같이 해봅니다.
:::

**프롬프트**

```
배포하기 전에, 배포하고 나서 뭘 확인해야 하는지 먼저 알려줘.
어느 화면의 어떤 기능을 봐야 하는지 목록으로.
```

배포 버튼 자체는 **Vercel 화면에서 클릭**으로 누릅니다. AI가 할 일이 아니에요.

## 5. 린트 — 코드 맞춤법 검사

**코드가 정해진 작성 규칙을 지켰는지 검사하는 일**입니다.

글을 쓰고 맞춤법 검사기를 돌리는 것과 같아요. 오타가 있는지, 나중에 문제가 될 만한 표현이 있는지 찾아줍니다.

**우리는 린트를 따로 시키지 않습니다.** 다만 프로젝트를 만들 때 자동으로 딸려 오고, **빌드할 때 같이 검사**돼요. 그래서 빌드 에러 중에 린트 문제가 섞여 있을 수 있습니다.

**프롬프트** — 빌드 에러에 린트가 섞여 있을 때

```
이 프로젝트의 린트를 실행해줘.

문제가 나오면 바로 고치지 말고, 어느 파일의 어떤 부분이
왜 문제인지 쉬운 말로 먼저 설명해줘.

내가 확인한 다음 필요한 부분만 고쳐줘.
```

:::note[린트를 통과했다고 다 되는 건 아니에요]
맞춤법이 맞다고 글이 잘 쓰인 건 아니듯이, 린트가 통과해도 **기능이 제대로 도는지는 따로 확인**해야 합니다.
:::

## 6. 리팩터링 — 겉은 그대로, 속만 정리

**화면이나 기능은 그대로 두고, 코드 내부만 정리하는 일**입니다.

방 안의 물건은 그대로 두고 찾기 쉽게 정리하는 것과 같아요. 같은 내용이 여러 곳에 반복돼 있거나 코드가 너무 길어졌을 때 짧고 읽기 쉽게 고칩니다.

**6회차 커리큘럼에서는 안 해도 됩니다.** 페이지가 3개뿐이라 정리할 만큼 복잡해지지 않아요.

시즌이 끝나고 계속 만들다가 "코드가 너무 지저분해졌다" 싶을 때 쓰시면 됩니다.

**프롬프트**

```
지금 기능과 화면은 바꾸지 말고, 코드만 읽기 쉽게 정리해줘.
중복되거나 너무 긴 부분을 정리해줘.

정리한 뒤에 기존 기능이 전처럼 작동하는지 확인하고,
무엇을 바꿨는지 쉬운 말로 알려줘.
```

:::caution[리팩터링 전에는 꼭 커밋부터]
겉모습이 그대로여야 하는데 **가끔 뭔가 깨집니다.**

<mark>리팩터링 전에 반드시 커밋해두세요.</mark> 그래야 이상해졌을 때 돌아올 수 있습니다.
:::

## 여섯 개를 관통하는 규칙 하나

위 프롬프트들을 다시 보시면, 전부 같은 말이 들어 있습니다.

> **아직 하지 말고 먼저 보여줘. 내가 좋다고 하면 그때.**

이게 이 문서에서 제일 중요한 부분이에요.

**우리는 Auto 모드를 씁니다.** 물어보지 않고 진행하니까 편한데, 대신 <mark>AI가 뭘 했는지 나중에 알게 됩니다.</mark>

그래서 되돌리기 어려운 일 — 커밋, 푸시, 배포, 리팩터링 — 앞에서는 **직접 멈춰 세우는 게 좋습니다.**

| 이 말을 붙이면 | 이렇게 됩니다 |
|---|---|
| `아직 하지 말고 먼저 보여줘` | AI가 계획만 말하고 멈춥니다 |
| `내가 좋다고 하면 그때` | 승인 전까지 손대지 않습니다 |
| `무엇을 바꿨는지 알려줘` | 끝나고 확인할 수 있습니다 |

## 자주 나오는 질문

**Q. 이걸 다 외워야 하나요?**
아니요. AI가 그 말을 썼을 때 "아 그거구나" 하시면 충분합니다. 필요할 때 이 문서를 다시 열어보세요.

**Q. 커밋과 푸시는 뭐가 다른가요?**
커밋은 **내 노트북에** 저장, 푸시는 그걸 **인터넷 창고로** 보내는 겁니다. 커밋만 하고 푸시를 안 하면 GitHub에는 아무것도 안 올라가요.

**Q. 빌드와 배포는 뭐가 다른가요?**
빌드는 **조립이 되는지 확인**, 배포는 **조립한 걸 공개**하는 겁니다. 빌드가 실패하면 배포도 안 됩니다.

**Q. 린트 에러가 났는데 그냥 무시하면 안 되나요?**
빌드를 막는 린트 에러는 무시할 수 없습니다. AI에게 설명을 듣고 고치시는 게 맞아요. 설정을 꺼서 넘기는 건 권하지 않습니다.
